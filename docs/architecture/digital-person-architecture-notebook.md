# Kumiko·Amadeus 数字主体架构改造记录本

> 状态：持续维护中的架构记录，不是最终实施规范。
>
> 建立日期：2026-08-08
>
> 维护规则：后续讨论中出现的新决定、被否决方向、数据结构、验收标准和未决问题，都追加到本文件；实施前再拆成正式 ADR、任务和迁移文档。

## 1. 项目最终目标与诚实边界

目标不是继续堆叠“像黄前久美子的提示词”，而是建立一个具备以下可观察能力的持续数字主体：

- 有统一、连续、不可任意重写的人生时间线。
- 能区分真实观察、他人陈述、工具结果、系统安排、推测和文学叙事。
- 知道自己一天做了什么，并能回忆当时注意到的细节和感受。
- 有选择性注意、记忆强化和自然遗忘，而不是全知全记。
- 有自己的需要、目标、承诺、计划、行动和行动结果。
- 用户不在线、客户端关闭或服务重启后，角色状态和未完成事务仍能延续。
- 经历能够改变后续信念、偏好、策略和目标，形成可追溯的成长。
- 图片、语音、视频和工具结果能成为带来源的经历，而不只是一次性 Prompt。
- 对外表达始终由统一的“久美子主体”产生，不因内部模块拆分而人格分裂。

当前工程可以追求并验收的是“持续主体型数字角色”和长期真人感。现有技术不能证明系统拥有意识、主观体验或与人类相同的生命；任何实现方案都不得把行为拟真直接宣称为意识诞生。

## 2. 总体结论

现有项目的基础方向没有错误，不应推倒重来。以下模块应当保留并逐步接入新核心：

- 角色身份、原作关系、世界书和人格护栏。
- 原始消息、时间 Episode、精确/时间/语义三路记忆查询。
- 桌面本地 RAG、Android RAG 和媒体存储。
- 学期、节假日、课表、Busy、睡眠和消息延迟等外部约束与表现机制。
- 模型供应商适配、TTS、图片输入、通知、备份和客户端 UI。
- 日记界面和用户体验，但日记的数据地位与生成方式必须重做。

需要重建的是：

1. 事实来源与人生事件账本。
2. 世界状态、自我状态和因果状态更新。
3. 需要、目标、承诺、计划与行动闭环。
4. 云端持久生命循环。
5. 内部认知与对外表达的职责拆分。
6. 日记、反思、成长与事实记忆之间的边界。
7. 可重复的长期评测体系。

## 3. 当前必须纠正的问题

### 3.1 生成的生活故事被提升成事实

当前 `DailyFragmentEntity` 主要保存日期、时间、文本和触发原因，没有来源、证据、可信度、因果关系和事实类别。`generateLifeFragment()` 使用模型推演离线生活，随后将结果作为“真实经历”纳入日记并进入 RAG。

这会形成污染链：

```text
模型想象事件
→ 生活切片被视为真实经历
→ 写进日记
→ 日记进入 RAG
→ 后续检索把它当历史证据
→ 新生成继续建立在旧虚构上
```

改正原则：

- 事实、推测和叙事必须使用不同的数据类型和检索命名空间。
- 模型可以创造虚拟世界事件，但生成后必须立即固化、标注来源，不能以后随意改写。
- 日记可以解释和表达经历，不能创造会影响未来的新事实。
- 没有事件支撑的具体日记主张必须删除、降级为不确定感受或明确标记为想象。

### 3.2 生命循环依附在客户端前端

当前主动消息、睡眠和日记结算主要由 React Hook 定时检查；离线生活在用户下一次发送消息时回填。客户端关闭后并不存在真正持续的状态推进，只能在下次启动时重建叙事连续性。

改正原则：

- 角色生命周期必须从 `useProactiveLifeCycle` 移到云端持久工作流。
- Electron、Android 和未来其他客户端只作为通信终端、缓存和展示层。
- 客户端关闭、云端 Worker 重启或网络中断，不能造成目标丢失、行动重复或时间线断裂。
- 本地模式可保留降级生命循环，但必须与云端使用同一套事件和状态接口。

### 3.3 随机主动消息被误认为自主性

当前主动消息主要由无互动时长、课表概率、关系热度和随机数决定。这能改善表现，但不能回答“她为什么现在想联系用户”。

改正原则：

- 主动联系必须首先产生可追溯的交流意图。
- 意图可能来源于承诺到期、目标进展、外界事件、需要表达、请求协助、关系维护或重要回忆触发。
- 随机数只用于自然化执行时间和抑制重复，不能成为行为原因。
- 每条主动消息应能追溯到 `intentId`、相关事件和触发条件。

### 3.4 记忆增长被误认为心智成长

把更多聊天、摘要和日记写入 RAG，只会增加可检索上下文，不会自动形成经验、信念修正、技能和行为策略变化。

改正原则：

- 成长必须表现为“经历 → 评价 → 反思候选 → 证据审核 → 信念/策略/目标更新”。
- 所有成长结果必须能追溯到支持事件。
- 不允许模型浏览互联网后自动修改权重或人格核心。
- 参数微调只用于后期优化表达和有限的决策偏好，不承载当天事实和个人记忆。

### 3.5 心理状态的因果方向需要调整

当前心理变量既受时间规则影响，也能被对话或日记生成的 delta 修改。若日记写得悲伤就反过来让角色更悲伤，会造成“叙事生成状态”的倒置。

正确方向：

```text
事件发生
→ 主观评价
→ 心理和需要变化
→ 当前心理影响日记口吻与对话表达
```

模型可以为事件提出评价标签，但数值更新应由确定性 reducer 执行，并记录来源事件。日记本身不是心理变化的原因。

### 3.6 对话、认知、工具和表现耦合过深

当前主聊天管线同时负责人格表达、记忆选择、事实核对、工具选择、情绪标签、状态 delta 和回复格式，工具循环也较浅。这使内部判断难以单独测试，也使“说得像真的”与“事实是真的”难以分开。

改正原则：

- 内部认知输出结构化提案，不直接对用户说话。
- 工具由代码执行，模型不能自行宣称完成。
- 对外表达模型只读取已经批准的主体状态和事实。
- 事实验证、权限审核和幂等控制必须由代码或独立验证模块完成。

### 3.7 缺少正式长期评测

当前项目缺少覆盖人格连续性、事实正确率、承诺履行、跨重启恢复和主动行为质量的版本化测试集。没有可重复评测，就无法判断改造是否让真人感提高，还是只让 Prompt 更复杂。

## 4. Multi-Agent 决策

### 4.1 是否需要 Multi-Agent

需要“职责拆分”，但不建议采用一群自由对话、互相投票的通用 Agent。推荐架构是：

```text
多个专职认知模块
+ 同一个不可变事件账本
+ 同一个世界/自我状态
+ 一个久美子主体协调器
= 统一数字主体
```

拆分的目的不是让多个模型分别扮演不同版本的久美子，而是让事实、记忆、目标、行动、审查和表达可以独立测试、替换和降级。

### 4.2 必须区分内部职责与可选世界人物模拟

当前项目只有一个主体和一个对话人格：黄前久美子。丽奈、秀一、叶月、绿辉等目前属于世界书、关系档案和日记上下文中的世界人物，不是独立 Agent，也不直接面向用户聊天。第一阶段改造不需要改变这一点。

本章所说的 Multi-Agent 首先是“久美子一个主体内部的职责型拆分”。下面的世界人物 Actor 只是未来在确实需要模拟复杂社会互动、并且普通状态机无法满足时才考虑的可选扩展，不是实现久美子持续主体所必需的前置条件。

#### A. 久美子内部的认知职责

这些模块都服务于同一个久美子，不拥有独立人格：

| 模块 | 职责 | 是否必须使用 LLM |
| --- | --- | --- |
| Event Ingestor | 接收时间、消息、传感器、工具结果并写入事件 | 否 |
| World Reducer | 从事件计算地点、课表、库存、关系等当前状态 | 否 |
| Self/Drive Reducer | 更新疲劳、压力、饥饿、社交需要等 | 主要否 |
| Perception/Appraisal | 判断她注意到什么、事件意味着什么 | 复杂事件时使用 |
| Memory Retriever | 选择原始事实、Episode、语义记忆和媒体 | 可混合 |
| Goal Manager | 维护目标、承诺、成功条件和截止时间 | 可混合 |
| Planner | 为目标提出下一步行动 | 需要时使用 |
| Action Policy | 审核权限、预算、风险和幂等 | 否 |
| Critic/Fact Validator | 检查提案是否有证据、是否矛盾 | 规则优先，LLM 辅助 |
| Reflection Module | 从事件提出经验和成长候选 | 使用 LLM |
| Dialogue/Expression | 将已批准状态表达成久美子的语言 | 使用主模型 |
| Diary Writer | 将当日事件写成私人日记 | 使用模型，但不能创造事实 |

不是每个模块都需要一个独立大模型调用。大量模块应是普通 TypeScript 服务。只有存在语义理解、取舍、计划或自然语言表达时才调用模型。

#### B. 世界中其他人物（可选扩展，当前不实施）

当前应继续把丽奈、秀一、叶月、绿辉等作为结构化世界人物档案：保存稳定身份、与久美子的关系、久美子已经知道的近况，以及有事件证据的状态变化。久美子的主模型可以根据这些已知资料描述或回忆他们，但不能把临时生成的他人私密思想当成事实。

只有未来出现以下明确需求时，才评估独立 Actor：

- 某个核心人物需要在久美子不在场时持续推进自己的目标和日程。
- 该人物的行动会反复、长期地影响久美子的世界事件。
- 仅用预设状态和事件规则已经无法保持其行为一致性。
- 产品明确需要模拟久美子与该人物之间的双向、长期社会互动。

即使满足这些条件，也不需要每个人 24 小时运行一个昂贵 Agent。建议按需唤醒，并分级处理：

建议分级：

- 普通路人：只用短期场景实体，不建立长期 Agent。
- 次要熟人：保存稳定身份、关系、近期状态和少量目标。
- 核心人物：只有经过单独立项后才拥有独立状态、目标、日程和事件记录；在与久美子发生交互或产生重要外部事件时按需唤醒 Actor Agent。
- 核心人物的私密想法默认不可被久美子直接读取；久美子只能依据对话、行动和已知历史形成自己的 `belief`。

若未来引入其他人物 Agent，其输出只能是“对世界采取了什么行动”，不能直接修改久美子的心理或记忆。行动先写入世界事件，久美子观察到后再形成自己的体验。

### 4.3 最终统合 Agent 的正确职责

最终统合者应命名为 `KumikoSelfCoordinator`，而不是模糊的“总模型”。它负责：

1. 收集已经过检索和验证的世界状态、自我状态、目标和相关记忆。
2. 处理专职模块提出的候选判断、计划和交流意图。
3. 按身份边界、当前目标、证据、风险和资源约束解决冲突。
4. 产生唯一的主体决策，例如行动、等待、改变计划或联系用户。
5. 把决策写成结构化记录，再交给执行器。
6. 只有需要对用户表达时，才把批准后的内部状态交给 Dialogue Agent。

它不能：

- 通过“少数服从多数”决定事实。
- 把多个 Agent 的自由文本简单拼接进最终回复。
- 绕过事件账本直接修改过去。
- 直接执行高风险工具。
- 读取其他人物没有向她展示的私密状态。

### 4.4 为什么不采用自由辩论式 Multi-Agent

自由辩论式 Multi-Agent 会带来：

- 多份互相冲突的事实版本。
- 人格被多个模型平均化。
- Token 成本和延迟成倍增加。
- 很难判断哪个 Agent 对错误负责。
- Agent 可能互相强化幻觉。
- 最终统合模型仍可能忽略所有意见。

因此采用“黑板/共享状态 + 结构化提案 + 单一主体决策”模式。共享黑板的事实部分就是事件账本和状态投影，不能由 Agent 自由重写。

## 5. 目标系统总架构

```text
用户消息 / 时间 / 天气 / 媒体 / 工具结果 / 世界人物行动
                              ↓
                         Event Gateway
                              ↓
                    Immutable Life Event Ledger
                   ↙          ↓           ↘
          World Projection  Self State   Memory Indexes
                   ↘          ↓           ↙
                    Goals / Commitments / Plans
                              ↓
                       Cognition Scheduler
                              ↓
                    Specialist Proposals
                              ↓
                   KumikoSelfCoordinator
                              ↓
                 Policy / Permission / Fact Check
                         ↙              ↘
                  Tool Execution      Dialogue Expression
                         ↓              ↓
                     Result Events    Message / Voice / Notice
                              ↓
                      Diary / Reflection / Consolidation
```

核心不变量：

- Event Ledger 是唯一事实源。
- 状态表是事件的可重建投影，不是独立真相。
- RAG 是检索索引，不是事实裁判。
- 日记是主观叙事，不是事件创建器。
- 工具结果必须重新写入事件账本。
- 所有模型输出默认只是提案，审核或执行后才成为状态变化。

## 6. 核心数据模型草案

### 6.1 `LifeEvent`

```ts
type EventSource =
  | 'observed'
  | 'user_report'
  | 'tool_result'
  | 'scheduled'
  | 'simulated_world'
  | 'inferred'
  | 'narrative';

interface LifeEvent {
  id: string;
  occurredAt: number;
  recordedAt: number;
  type: string;
  actor: 'kumiko' | 'user' | 'system' | string;
  source: EventSource;
  payload: Record<string, unknown>;
  evidenceEventIds: string[];
  confidence: number;
  causationId?: string;
  correlationId?: string;
  idempotencyKey?: string;
  visibility: 'private' | 'shared' | 'system';
}
```

强事实默认只包括：

- `observed`
- `tool_result`
- `scheduled`
- 明确标记为“用户如此陈述”的 `user_report`
- 已经由虚拟世界引擎提交且固化的 `simulated_world`

`inferred` 必须携带可信度和证据，不能在精确事实问题中伪装成确定答案。`narrative` 永远不能证明客观事件。

### 6.2 其他表

| 表 | 关键字段与职责 |
| --- | --- |
| `beliefs` | subject/predicate/object、confidence、evidenceEventIds、validFrom/validTo、supersededBy |
| `drives` | 当前值、基线、更新时间、来源事件、衰减规则 |
| `goals` | origin、priority、status、successCriteria、deadline、nextReviewAt |
| `commitments` | 对象、内容、承诺时间、截止时间、履行/失败/取消证据 |
| `plans` | goalId、步骤、依赖、状态、下一动作 |
| `actions` | tool、参数摘要、权限、幂等键、开始/完成时间、resultEventId |
| `reflections` | 支持事件、经验候选、置信度、审核状态、产生的 belief/goal |
| `memoryLinks` | 事件、原始消息、Episode、向量、媒体和日记之间的引用 |
| `diaries` | 正文、引用事件、事实主张审核、实际写作时间、生成状态 |
| `syncCursors` | 客户端、设备、云端最后同步序号和冲突信息 |

## 7. 真正“度过一天”的事件驱动心智

### 7.1 不需要每秒运行模型

没有新刺激时：

- 时间继续前进。
- 课表和位置按确定性规则变化。
- 精力、压力、饥饿、困倦等按规则积分。
- 目标和承诺的截止时间继续接近。
- 当前行动保持进行中。

只有发生值得注意的事件时才唤醒认知模型，例如：

- 用户消息。
- 日程节点变化。
- 承诺或目标到期。
- 工具返回。
- 意外天气或外界信息。
- 世界人物发起互动。
- 某项计划失败。
- 每日晚间反思。

### 7.2 单次认知循环

```text
1. 写入刺激事件
2. 使用 reducer 推进世界和身体状态
3. 加载未完成目标、承诺和相关事实
4. Attention Gate 判断是否需要模型推理
5. 专职模块生成结构化候选
6. KumikoSelfCoordinator 选择主体决策
7. 事实、权限、预算、风险和幂等审核
8. 执行工具、等待或创建未来任务
9. 将结果写回事件账本
10. 更新状态投影和记忆索引
11. 决定是否产生对用户的交流意图
```

### 7.3 细节认知

每个值得记忆的事件分为：

- 客观事件：时间、地点、人物、动作和结果。
- 感知内容：她实际注意到了哪些声音、物体、话语和变化。
- 主观评价：愉快度、意外度、重要度、控制感和目标关联。
- 记忆强度：以后保留哪些细节，哪些可以自然衰减。

没有被观察或记录的细节不应在以后被精确回答。允许诚实地说“记不清了”，而不是现场补写。

### 7.4 虚拟世界而非自由写作

若要让她在宇治拥有独立生活，需要一个简化但持久的虚拟世界状态：

- 学校、教室、办公室、住宅、车站和常走路线。
- 当前课程进度、待批改作业、部活事务。
- 家庭库存、待办、物品位置。
- 重要人物的日程、关系和近期事件。
- 天气、节假日和公开现实信息。

世界状态先决定“什么可能发生”，模型再决定“她注意什么、怎样理解和选择”。不能让模型每次从空白 Prompt 自由创作整个世界。

## 8. 日记系统必须重做

### 8.1 四层拆分

| 层次 | 含义 | 是否事实源 |
| --- | --- | --- |
| Daily Timeline | 当天实际发生的事件时间线 | 是 |
| Private Diary | 久美子对事件的第一人称主观叙述 | 否 |
| Daily Reflection | 经验、疑问、失败和计划候选 | 候选，不直接生效 |
| Memory Consolidation | 决定长期保留的事件和线索 | 索引，不创造事件 |

### 8.2 新生成流程

```text
当天 LifeEvents
→ 筛选她参与或注意到的事件
→ 构建按时间排序的经历包
→ 生成第一人称日记
→ 抽取日记具体主张
→ 每项主张绑定 eventIds
→ 无证据主张删除、降级或明确标记为想象
→ 保存日记
→ 提取反思、记忆和目标候选
→ 独立验证后更新对应系统
```

### 8.3 日记规则

日记可以自由表达：

- 语气、措辞和吐槽。
- 已发生事件引起的感受。
- 对旧记忆的联想。
- 自我评价、担忧和期待。
- 不改变事实的感官化表达。

日记不能自行创造：

- 新人物和新对话。
- 新地点、购买、电话、约会或外部行动。
- 会影响未来的承诺。
- 未发生但以后会被当成事实的情节。

核心规则：日记可以解释经历，不能创造经历。

### 8.4 日记元数据

```ts
interface DiaryEntry {
  id: string;
  date: string;
  writtenAt: number;
  body: string;
  summary: string;
  referencedEventIds: string[];
  unsupportedClaims: DiaryClaim[];
  emotionalThemes: string[];
  reflectionCandidateIds: string[];
  memoryCandidateIds: string[];
  goalCandidateIds: string[];
  generationStatus:
    | 'written_on_time'
    | 'written_late'
    | 'reconstructed'
    | 'incomplete';
  validationStatus: 'passed' | 'partial' | 'failed';
}
```

补写日记必须保存真实 `writtenAt` 并标记 `reconstructed`，不能假装当晚已经写过。

### 8.5 日记与心理状态

日记不能直接生成并应用 psyche delta。心理变化应由事件和评价决定；日记只表达已经存在的心理状态。日记反思可以提出新的 belief、goal 或策略候选，但必须经证据审核后才生效。

## 9. 记忆与 RAG 重构

至少拆分以下检索空间：

| Namespace | 内容 | 可否作为事实证据 |
| --- | --- | --- |
| `fact_events` | 事件账本中的强事实 | 可以 |
| `raw_dialogue` | 用户和久美子的原始消息 | 可以证明说过什么 |
| `temporal_episodes` | 派生的对话章节 | 只能摘要辅助 |
| `beliefs` | 久美子当前相信的内容 | 必须显示可信度 |
| `subjective_diary` | 私人日记 | 只能证明她如何叙述/感受 |
| `reflections` | 已审核经验 | 可以解释策略变化 |
| `canon` | 原作和稳定世界设定 | 稳定背景事实 |
| `narrative` | 文学化内容 | 不得证明客观事件 |

查询路由示例：

- “你昨天去哪里了？”优先 `fact_events`。
- “我昨天原话是什么？”只用 `raw_dialogue`。
- “你昨天心情怎么样？”使用事件评价、self state 和 `subjective_diary`。
- “你最近为什么总是早点睡？”使用 `reflections`、目标和行为策略。

## 10. 云端持久运行

### 10.1 推荐生产结构

- TypeScript API/Worker，与现有代码语言一致。
- PostgreSQL 作为云端权威事件和状态数据库。
- pgvector 保存可事务关联的向量索引。
- Temporal 或同类耐久工作流承载跨天计划、定时唤醒、重试和崩溃恢复。
- S3 兼容对象存储保存加密图片、音频和视频。
- WebSocket/推送服务向客户端发送消息和状态更新。
- Electron/Android Dexie 保留为加密缓存、离线读和待同步事件队列。

### 10.2 工作流约束

- 每个角色实例拥有一个持久 Workflow 或等价的单主体串行调度上下文。
- LLM 和外部 API 调用放在可重试 Activity 中，不能直接放在必须确定性重放的 Workflow 逻辑中。
- 所有外部动作必须有 `idempotencyKey`。
- 同一角色的状态变更需要串行提交或使用明确的乐观并发版本。
- 工作流历史过长时使用 continue-as-new 或等价快照机制。

### 10.3 渐进迁移

先在本地实现 Event Ledger 和认知接口，再移动到云端。不要一开始同时重写数据库、云端、UI、RAG 和所有角色逻辑。

### 10.4 是否必须使用 VPS

如果要求“用户电脑关机后角色仍继续运行”，就必须有某种始终可被唤醒的外部计算环境，但它不一定是传统 VPS。可选形态：

| 形态 | 是否需要用户购买 VPS | 特点 |
| --- | --- | --- |
| 本机常驻 | 否 | 电脑必须开机且不能深度休眠；最接近现有 Electron 架构 |
| 官方托管服务 | 否 | 项目方维护云端，普通用户注册后直接使用 |
| 用户自托管 | 是或使用自己的家用服务器 | 用户掌握数据和服务，但需要维护部署 |
| 托管容器/Serverless/Durable Entity | 否 | 云平台按需唤醒，减少运维；受平台能力和地区网络约束 |

VPS 只是最直接的原型方案。若云端只运行事件调度、数据库和 API，LLM/Embedding 仍调用外部服务，单个私人实例不需要 GPU。不要在单用户小 VPS 上一开始就自托管完整 Temporal 集群；原型可先采用单 Node.js Worker + PostgreSQL 持久任务表和幂等执行器，稳定后再迁移到托管耐久工作流或更完整的工作流平台。

### 10.5 对外提供时的三种产品模式

同一个客户端和同一套核心代码应支持三种模式，不为每个用户复制或重写代码：

```text
LOCAL_ONLY   本地运行，电脑关闭时生命循环暂停或仅做明确的状态补偿
HOSTED       项目方托管，多用户各自拥有隔离的角色实例
SELF_HOSTED  用户使用统一 Docker 镜像在自己的 VPS/NAS/服务器部署
```

推荐顺序：

1. 当前开发阶段保持 `LOCAL_ONLY`，先完成统一事件协议。
2. 为本人建立一个单租户 `HOSTED` 原型，验证云端持续运行。
3. 把单租户原型改造成从第一天就携带 tenant/instance 标识的数据模型。
4. 稳定后同时提供普通用户托管版和高级用户自托管包。

### 10.6 多租户隔离模型

必须区分以下身份：

```text
Account                登录账户
Tenant/Workspace       数据和计费边界；个人使用时通常一人一个
CharacterInstance      某位用户自己的久美子实例
Device                 该用户授权的桌面或手机
```

所有权关系：

```text
Account
└── Tenant
    └── CharacterInstance
        ├── LifeEvents
        ├── Beliefs / Goals / Plans
        ├── Messages / Memories / Diaries
        ├── Media
        ├── Workflow
        └── Encryption Key
```

所有权威表至少携带：

```ts
interface TenantScopedRecord {
  tenantId: string;
  characterInstanceId: string;
  id: string;
  version: number;
}
```

建议约束：

- 所有唯一键都包含 `tenantId` 或 `characterInstanceId`。
- 每个角色工作流 ID 使用 `character:{tenantId}:{characterInstanceId}`。
- 每个角色拥有独立顺序号，主体状态修改在该实例内串行提交。
- PostgreSQL 使用 Row-Level Security 作为数据库侧第二道隔离，应用服务仍需显式检查 tenant。
- 对象存储使用不可猜测对象键、服务端授权和每租户加密键；不能只依靠文件路径前缀隔离。
- 日志和评测数据也必须脱敏并携带租户边界。
- 管理员支持功能采用审计、临时授权和最小权限，不能默认读取用户日记和媒体。

用户 A 的模型请求永远不能加载用户 B 的消息、事件、向量、日记、媒体或私有 Prompt。公共内容只包括版本化的角色基础设定、原作世界书和应用代码。

### 10.7 每个用户如何获得“自己的久美子”

创建新实例时执行：

```text
读取公共、只读的 Kumiko Canon Seed
→ 创建全新的 characterInstanceId
→ 创建空 Life Event Ledger
→ 写入实例出生/初始化事件
→ 生成独立加密键和工作流
→ 用户完成自己的位置、时区、模型和隐私配置
```

绝不能复制开发者本人的：

- 对话历史。
- 日记和生活事件。
- 关系进展和好感状态。
- 用户画像、提醒和私人锚点。
- API Key 和加密密钥。
- 从本人数据微调出的、包含可识别私人信息的专属权重。

公共人格种子可以相同，但每个实例从空白个人经历开始，因此之后会形成不同的人生、记忆和关系。

### 10.8 官方托管版

普通用户不购买 VPS。项目方运行：

- 账户与设备认证服务。
- 角色实例路由和持久工作流。
- PostgreSQL/向量数据库。
- 媒体对象存储。
- 推送、WebSocket 和备份服务。
- 模型调用、配额和账单系统。

可采用共享基础设施中的逻辑隔离；高隐私或付费用户以后可以升级为独立数据库、独立工作流 Namespace 或独立数据平面。初期不必每用户一台服务器，否则成本和运维会线性增长。

当前 `AuthScreen` 的本地用户名/密码保存在 `localStorage`，不属于真正的云端身份认证。托管版需要服务端账户、短期访问令牌、刷新令牌/设备会话、撤销和速率限制；客户端不能自行声明 tenantId。

### 10.9 用户自托管版

自托管不等于拆分源码或单独重写配置。应发布统一版本的容器镜像和 `compose.yaml`，包含：

- `character-api`
- `character-worker`
- `postgres`
- 可选的对象存储或外部 S3 配置
- 可选的反向代理

用户只需要：

1. 准备 VPS/NAS/家庭服务器和域名或安全隧道。
2. 安装 Docker Engine 与 Compose。
3. 填写 `.env` 或使用初始化向导配置域名、模型 Key、管理员凭据和加密密钥。
4. 执行统一部署命令。
5. 在客户端扫描配对码或填写自己的服务器地址。

升级使用统一镜像版本和数据库 migration，不允许长期维护用户专属代码分支。配置差异全部通过环境变量、数据库配置和 feature flags 表达。

自托管包必须提供：

- 自动数据库迁移和失败回滚说明。
- 健康检查、备份、恢复和升级命令。
- 首次启动生成的随机管理员密钥。
- TLS/反向代理示例。
- 密钥轮换和设备撤销。
- 不含任何开发者私人数据的公共角色种子。

### 10.10 数据导出与部署模式迁移

定义版本化 `Character Bundle`：

- 事件账本。
- 状态快照和 schema 版本。
- 原始对话、Episode、日记和反思。
- 媒体清单及加密媒体文件。
- 用户配置、世界书扩展和模型偏好。
- 向量索引可选择重建，不必作为唯一数据源迁移。

密钥、登录令牌和提供商 API Key 默认不进入普通导出包。托管版迁移到自托管版时，新服务重新生成实例密钥并重建索引；导入操作必须创建明确的迁移事件。

### 10.11 控制平面与角色数据平面

为以后扩展，逻辑上拆成：

```text
Control Plane
  账户、套餐、设备、实例创建、版本、部署和运维

Character Data Plane
  某个实例的事件、记忆、工作流、媒体、模型调用和通知
```

自托管用户可以完全拥有自己的 Data Plane；若仍使用官方账户做许可证或更新检查，也不应因此让官方服务默认读取角色私有数据。

### 10.12 VPS、域名与应用内自托管连接

可以直接使用本人或其他用户已有的 VPS、NAS、家庭服务器和域名，但必须区分两个完全不同的地址：

```text
模型提供商地址 / AI customEndpoint
  只决定聊天、视觉等模型请求发往哪里

角色服务器地址 / Character Server URL
  承载身份、设备配对、事件账本、时间流、记忆、日记、任务、媒体和同步
```

当前项目只实现了第一类地址。`AIConfigScreen` 的“使用自定义接口”可以将部分模型调用指向兼容 API 或代理，但这不会自动把角色生命周期和数据迁移到 VPS。当前 `AuthScreen` 和账户设置仍读取 `localStorage` 中的本地用户名、密码；`electron-main.cjs` 也明确删除了旧的 Fastify 移动访问服务。因此不能把现有自定义模型地址误认为完整自托管连接。

目标客户端增加独立的“部署与连接”设置，不与模型设置混在一起：

```ts
type DeploymentMode = 'LOCAL_ONLY' | 'HOSTED' | 'SELF_HOSTED';

interface ServerConnectionConfig {
  mode: DeploymentMode;
  baseUrl: string;              // 例如 https://kumiko.example.com
  deviceId: string;
  tenantId: string;
  characterInstanceId: string;
  serverFingerprint: string;
}
```

刷新令牌、设备私钥等秘密不得放入这个普通配置对象或 `localStorage`，应保存在操作系统安全凭据存储中。客户端也不能让用户手工填写或自行声明 `tenantId` 与 `characterInstanceId`；这些标识由服务器完成配对后签发。

推荐的用户体验：

1. 用户在自己的服务器上运行统一版本的 Docker Compose 自托管包。
2. 初始化向导让用户填写域名、模型提供商配置和管理员信息，并生成实例密钥。
3. 服务器生成短时有效、仅可使用一次的配对码或二维码。
4. 用户在应用中选择“连接自己的服务器”，只填写 `https://kumiko.example.com` 和配对码，或直接扫码。
5. 客户端访问 `/api/v1/health`、`/api/v1/version` 和 `/api/v1/capabilities`，检查 TLS、协议版本、服务器身份及可用能力。
6. 配对成功后服务器签发短期访问令牌、可轮换的设备会话，并返回该用户自己的 tenant 和角色实例标识。
7. 后续升级只更新统一镜像并执行数据库 migration；任何用户都不需要复制项目、改源码或维护个人代码分支。

服务器最小可行组成：

```text
域名 DNS
  → Caddy/Nginx/Traefik（HTTPS、WSS、上传限制、反向代理）
    → character-api（认证、同步、查询、推送）
    → character-worker（事件驱动生命循环、日记、记忆整理、任务）
    → PostgreSQL（权威数据、持久任务表；以后可加入 pgvector）
    → 媒体存储（原型可用加密磁盘目录，正式版使用 S3 兼容存储）
    → 模型网关（外部 API、远端 GPU 或用户自己的模型端点）
```

域名本身只提供稳定、易记的网络入口，不能代替 VPS 上的计算和数据库。三种连接方式都应支持：

| 方式 | 用户填写 | 适用情况 |
| --- | --- | --- |
| 公网域名 | `https://kumiko.example.com` + 配对码 | 跨网络、跨设备；推荐正式使用 |
| Tailscale/私网域名 | 私网 HTTPS 地址 + 配对码 | 个人高隐私使用，不开放公网端口 |
| IP 地址 | HTTPS IP 地址 + 配对码 | 仅在证书正确时正式支持；明文 HTTP 只允许开发环境 |

不能要求普通用户在客户端填写 PostgreSQL 密码、Docker 密钥、服务器管理员密钥或对象存储密钥。模型 API Key 可提供两种明确模式：服务器保管的 BYOK，或官方托管计费；无论哪种都不能作为普通客户端明文偏好长期保存。

每位用户一台自己的 VPS 时，部署天然形成物理隔离，但应用层仍必须保留 tenant、角色实例和设备权限检查，以防配置错误及以后迁移到共享托管。若一台 VPS 同时承载多个用户，则所有权威表、对象和任务必须带租户边界，并使用 PostgreSQL Row-Level Security 作为第二道隔离。

个人原型不必立即引入完整 Temporal 集群。首先使用 `character-api + character-worker + PostgreSQL 持久任务/outbox 表 + Caddy + Docker Compose`，已经能够在电脑关机后继续时间推进、事件结算、日记生成和消息推送。待跨天任务、重试和并发规模证明现有执行器不足后，再迁移到耐久工作流平台。

如果推理仍调用外部模型 API，普通 CPU VPS 即可承载上述心智编排和数据层：试验可从 2 vCPU、4 GB 内存起步，较稳妥的个人版为 4 vCPU、8 GB 内存和 80～100 GB SSD。图片、音频和视频增长很快，正式使用应启用对象存储、配额、备份和生命周期清理策略。若要在同一 VPS 自托管大语言模型，则需要另按模型规模配置 GPU，不能把普通 CPU VPS 当作高质量本地推理机。

### 10.13 离线期间的持续生活与主动消息

VPS 最重要的用途不是作为普通 API 中转，而是成为角色不依附任何一台用户设备的常驻生活载体。即使电脑和手机全部关闭，久美子的服务端角色实例仍应按自己的时区、日程、目标、身体/心理状态和已确认世界状态处理到期事件，并可能在当时决定联系用户。

这项能力会明显增加真人感，因为它带来四种当前本地前端循环没有的体验：

- 用户不发 Prompt 时，时间和因果仍然前进。
- 久美子可以在真实的某一时刻想到用户并发出消息，而不是等待用户唤醒。
- 用户缺席期间发生的事会进入后续记忆、日记、情绪和计划。
- 消息的“写出时间”和“用户收到/读到时间”不同，形成真实的异步关系。

但它只有在消息确实于服务端当时生成并持久化时才成立。禁止在客户端重新上线后临时生成一批消息，再伪造为几小时前发送；这种事后补写一旦出现时间、事件或记忆矛盾，会比没有离线消息更破坏真人感。

正确因果链：

```text
持久调度器在 dueAt 唤醒
→ 结算结构化 LifeEvent
→ 更新日程、位置、目标、心理/身体状态和记忆候选
→ KumikoSelfCoordinator 判断这件事是否值得联系用户
→ 若决定联系，立即生成 OutboundMessage 并写入服务器
→ 有在线设备时实时推送；无在线设备时保持 queued
→ 任一设备上线后按 serverSequence 增量同步
→ 客户端保留原 authoredAt，并另外记录 deliveredAt/readAt
→ 此事件和消息参与当天日记及以后回忆
```

不是每个生活事件都要变成消息。真人会经历大量没有告诉别人的片段，也会有一整段时间没有想发消息。是否联系用户应综合：事件显著性、当前目标、当时情绪、关系边界、近期联系频率、安静时间、是否已有未读消息和用户主动消息偏好，而不是每十分钟做一次固定随机抽奖。

建议的服务端消息模型：

```ts
interface OutboundMessage {
  id: string;
  tenantId: string;
  characterInstanceId: string;
  serverSequence: number;
  body: string;
  causeEventIds: string[];
  authoredAt: number;       // 久美子在服务器上真正形成消息的时间
  queuedAt: number;
  firstDeliveredAt?: number;
  readAt?: number;
  state: 'queued' | 'pushed' | 'synced' | 'read';
  origin: 'offline_proactive' | 'online_proactive' | 'reply' | 'reminder';
  generationMode: 'real_time' | 'recovery_catch_up';
}
```

事件本身另有 `occurredAt`。例如练习在 16:20 结束、久美子在 16:47 想起用户并写消息、用户于 21:03 开机同步，这三个时间不能压成一个 `timestamp`。多设备场景还需要独立的 `MessageDelivery` 记录；用户若已在手机读过，之后打开电脑不应再次显示为全新未读。

客户端重新上线后的推荐呈现：

```text
──────── 你不在的时候 · 3 条 ────────
16:47  久美子：……
19:12  久美子：……
20:36  久美子：……

──────── 你回来了 · 21:03 ────────
```

历史消息应立即按原时间进入会话，不播放成“她此刻正在输入”，也不把同步时间显示成发送时间。可以使用轻微的加载动画，但必须清楚区分：

- `authoredAt`：她当时发出的时间，聊天气泡主要显示这个时间。
- `deliveredAt`：设备实际收到时间，只在消息详情或“离线期间送达”状态中显示。
- `readAt`：用户真正看到或打开会话的时间。
- `occurredAt`：导致她发消息的生活事件时间，只用于因果、记忆和审计，不必直接暴露在聊天气泡。

服务端只能可靠知道“当前没有活跃设备会话”，不能断言用户关机、睡觉或在做什么。因此 UI 和话术使用“你不在的时候/离线期间”，不要让久美子声称知道用户具体为何不在线。

服务器若因故宕机，恢复后可以按事件规则进行 `recovery_catch_up`，但必须保留恢复来源和真实生成时间。它可以结算错过的日程事件，却不能把恢复时生成的主动消息伪装成宕机期间已经发出。真正的实时离线消息与灾后推演必须具有不同 provenance。

现有 `useProactiveLifeCycle` 只能在 React 应用处于 `APP` 状态时运行，并以十分钟轮询、三小时空窗和随机概率触发；`triggerNativeProactiveMessage` 随后把消息直接加入本机 store。该实现可以保留为 `LOCAL_ONLY` 降级模式，但云端模式必须将调度、事件结算、主动决策、消息生成和 outbox 全部迁入持久 Worker。现有单一 `Message.timestamp` 也需要升级为上述多时间语义。

这项能力是高收益的真人感基础设施，但不是充分条件。若生活事件只是模型随机编故事、消息没有可追溯原因、日记无法引用同一事件，仍然只是更频繁的角色扮演。验收时必须确认每条离线主动消息都能回溯到当时存在的事件、状态或目标，且久美子后来能一致地记得“为什么那时发了这条”。

### 10.14 VPS 权威运行与 iOS 完整能力边界

可以把角色的权威心智和生活系统几乎全部放在 VPS：生命循环、事件账本、状态、记忆、日记、计划、主动决策、消息 outbox、模型调用、媒体处理和多设备同步都不依赖 iPhone 是否运行。也可以从 VPS 提供 Web 前端。但若要求 iOS 获得通知、系统来电界面、麦克风、摄像头、语音播放和本机权限，就不能彻底取消原生客户端。

目标形态应是“服务器主体 + 薄客户端”，而不是在 iPhone 后台复制一套主体：

```text
VPS / Private Cloud（权威主体）
  Life Worker + KumikoSelfCoordinator
  Event Ledger + Memory + Diary + Outbox
  Model Gateway + Realtime Voice Session
  APNs / Push Gateway
                  │
                  ▼
iOS Thin Client（身体与窗口）
  UI + encrypted cache + sync cursor
  Keychain device credential + APNs/PushKit token
  Notification handler + CallKit
  microphone/camera/speaker + AVAudioSession
```

iOS 客户端不应运行持续生命循环，也不能依赖常驻 WebSocket 或任意后台定时器。苹果可能暂停应用，后台静默通知也是低优先级且不保证送达；持续时间和事件必须由 VPS 推进，iOS 只在收到系统允许的唤醒或用户打开应用时同步。

能力边界：

| 能力 | iOS 是否可做 | 正确实现 |
| --- | --- | --- |
| 设备关闭时久美子继续生活 | 是 | VPS Worker 运行，与 iOS 无关 |
| 应用退出时收到主动文字消息 | 是，但依赖用户授权和 APNs | VPS 写入 outbox 后发送普通 alert push |
| 手机离线后重新打开加载所有消息 | 是 | 客户端按 serverSequence 从 VPS 补齐，不能依赖 APNs 保存完整历史 |
| 锁屏/后台显示真正的来电界面 | 有条件可做 | PushKit VoIP push + CallKit + 可立即连接的实时双向语音会话 |
| 用来电界面伪装普通提醒或吸引注意 | 不应做 | 使用普通通知；PushKit 只用于真实网络语音呼叫 |
| 接听后和久美子实时语音对话 | 是 | CallKit 管系统状态，客户端与 VPS 建立 WebRTC/实时音频连接 |
| 后台永久运行 JS、模型和心智循环 | 否 | 全部迁到 VPS |
| 应用被关闭时持续使用摄像头/麦克风观察 | 否 | 只有前台或合规的活跃音频会话中、经授权使用 |
| 复刻桌面端任意电脑控制 | 否 | 受 iOS 沙箱限制，只能使用公开 API、App Intents 和用户授权能力 |

普通主动消息采用双保险：

1. 消息正文和所有时间首先永久写入 VPS outbox。
2. VPS 向 APNs 发送提醒；它只是“有新消息”的通知通道，不是消息数据库。
3. APNs 可能在设备离线时暂存通知，但可能合并或覆盖同一应用的多条待送通知。
4. iPhone 上线或应用打开后始终向 VPS 做增量同步，因此即使通知被系统丢弃，历史消息也不会丢失。
5. 用户若关闭通知权限，仍可在下次打开应用时看到完整的“你不在的时候”消息。

真正的 iOS 来电流程：

```text
久美子在 VPS 形成 CallInvitation（短时有效）
→ Push Gateway 向 APNs 发送 VoIP push
→ PushKit 唤醒/启动 iOS 客户端
→ 客户端立即向 CallKit reportNewIncomingCall
→ iOS 显示系统来电界面
→ 用户接听
→ 客户端连接 VPS 实时语音会话
→ 通话事件、摘要和可记忆内容按权限回写事件账本
```

VoIP 来电不能像离线文字消息一样排队几小时后再响。苹果建议 VoIP push 的过期时间为 0 或仅几秒；设备当时不可达时，服务器应将其转成“未接来电”事件和普通消息，待用户上线后显示，而不是迟到数小时突然弹出来电。

AI 主动来电在技术上可以形成真实双向网络语音会话，但公开上架时仍存在审核解释风险。必须让用户明确开启并配置可呼叫时段、频率和勿扰规则；接听后必须马上存在真实可用的音频会话。不能仅为了模拟真人或播放一段预录语音而滥用 PushKit/CallKit。更保守的首版使用普通通知“久美子想和你通话”，用户点击后进入应用内通话；确认审核路径后再升级系统来电。

自托管 iOS 还有一个关键基础设施问题：同一个官方签名 App 的 APNs 和 PushKit 提供商凭据由应用开发者持有，不能把全局 `.p8` 密钥分发给每位自托管用户的 VPS。推荐两种模式：

```text
普通自托管用户：自己的 VPS → 官方最小 Push Relay → APNs → 自己的 iPhone
完全独立用户：自行签名 iOS App + 自己的 Apple Developer/APNs 凭据 → APNs
```

官方 Push Relay 只接收签名后的最小投递指令和设备路由，正文可保持通用提示或端到端加密；它不应读取角色事件账本、日记或模型配置。Relay 故障时只影响即时系统提醒，不影响 VPS 上的生活、消息持久化和下次启动同步。

当前仓库还没有上述 iOS 能力。现有 CI 只生成并上传 Capacitor `ios/` 工程，不是用户发行版；依赖中只有本地通知插件，没有远程 push 插件；`capacitorNotifications.ts` 明确是 Android-first，Android FullScreenIntent/CallStyle 插件在非 Android 平台直接退出。iOS 版本需要新增 Swift 原生层、APNs 注册、PushKit、CallKit、AVAudioSession、服务器 Push Gateway、签名和真机测试。

推荐实施顺序：

1. 先完成 VPS 事件账本、outbox、增量同步和多时间戳，保证消息绝不依赖推送可靠性。
2. 建立原生 iOS 薄客户端与 Keychain 设备配对。
3. 接入普通 APNs 主动消息并验证前台、后台、应用未运行、锁屏、离线重连和通知被关闭场景。
4. 完成前台实时语音会话及中断恢复。
5. 再接入 PushKit + CallKit，仅承载真实的短时有效实时语音邀请。
6. 使用实体 iPhone、正式签名和 TestFlight 验证 Focus、弱网、设备重启、Token 轮换、多设备已读和 App Review 合规。

参考：Apple 的 [远程通知服务器](https://developer.apple.com/documentation/usernotifications/setting-up-a-remote-notification-server)、[后台更新通知](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)、[PushKit VoIP 通知](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit) 和 [CallKit VoIP 呼叫](https://developer.apple.com/documentation/callkit/making-and-receiving-voip-calls) 文档。

## 11. 多模态感知

每段媒体必须保存：

- 原始媒体 URI 或本地路径。
- 内容哈希。
- 采集时间和来源设备。
- 用户授权范围。
- 模型观察结果。
- 观察置信度。
- 时间片段或画面区域。
- 关联事件和记忆 ID。

模型对媒体的描述只是 perception proposal。只有系统确认媒体存在、时间来源明确且结果通过格式校验后，才能写入 observed/inferred 事件。

实时语音/视频模型是感知和表达通道，不应成为唯一记忆存储。实时会话结束后仍需生成结构化事件、原始转录引用和媒体索引。

## 12. 成长与训练

### 12.1 可追溯成长

```text
经历事件
→ 主观评价
→ 多次模式被识别
→ 反思候选
→ 证据审核
→ 新信念、策略或目标
→ 后续行为变化
```

示例：

```text
连续三次深夜聊天后第二天精力不足
→ 形成“深夜聊天会影响工作”的经验
→ 创建更早结束聊天的策略
→ 下次提前表达困倦并结束交流
```

### 12.2 微调边界

前期不进行自动在线权重更新。积累足够且人工筛选的数据后，微调只用于：

- 久美子的语言风格。
- 不同心理状态下的表达差异。
- 有限的决策偏好。
- 工具选择和结构化输出稳定性。

不微调进入权重的内容：

- 当天发生的个人事实。
- 用户隐私和聊天记忆。
- 持续变化的现实知识。
- 未审核互联网内容。
- 模型自己生成后又拿来训练自己的文本。

### 12.3 完全本地模型替代策略与硬件档位（2026-08-08 快照）

“完全不用第三方大模型 API”不等于“只运行一个全能模型”。正确方式是保留统一的 `ModelGateway`，把第三方地址替换为自己控制的本地或私有云推理端点，并使用可独立装卸的模型服务：

- 主脑：文字对话、图片/抽帧视频理解、计划、反思和工具调用提案。
- 语音识别：只负责语音转写；环境声音、语气和非语言信号另做观察事件。
- 语音合成：只负责把最终话语转成声音，不参与事实和决策。
- Embedding/Reranker：只负责记忆检索，继续可使用本地 BGE-M3。
- 确定性运行时：系统时间、日历、定时器、事件账本、日记管线、权限检查和工具执行都由代码完成，不交给模型“记住”。

当前候选组合：

- 低配原型：`Qwen3.5-4B` 量化版作为主脑，配轻量本地 ASR/TTS；可以验证闭环，但不可作为“接近真人”的质量目标。
- 中档试用：`Qwen3.5-9B` 量化版；人物语言和视觉能力明显提高，但长期细腻关系、多步工具和复杂自我反思仍会频繁露出模型感。
- 推荐个人版：`Qwen3.6-35B-A3B` 的成熟 4-bit/5-bit 部署作为文字、视觉、视频抽帧和工具主脑，语音使用独立 ASR/TTS。它有 35B 总参数、每次约 3B 激活，但全部权重仍需存入显存或内存；“3B 激活”不等于只占 3B 模型空间。
- 高端质量版：`Qwen3.5-122B-A10B-GPTQ-Int4` 或后续同档模型。官方 Int4 仓库本身约 78.9 GB，实际服务还需要 KV cache、视觉编码器和运行时空间，因此 80 GB 只是极紧边界，96 GB 或多卡更合理。
- 原生全模态实验：`Qwen3-Omni-30B-A3B` 可直接处理文字、图片、音频和视频并输出文字/语音，但官方 BF16 理论最低显存随 15/30/60/120 秒视频约为 78.85/88.52/107.74/144.81 GB；不适合消费级笔记本常驻。

硬件规划：

| 档位 | 可用显存 | 适合目标 | 结论 |
|---|---:|---|---|
| 当前笔记本 | RTX 4070 Laptop 8 GB；系统内存 16 GB | 4B 量化原型；9B 极限短上下文、模型轮换 | 可开发和验证，不能流畅承载目标完整版 |
| 入门桌面 | 24 GB；系统内存 64 GB | 9B 稳定运行；35B 高压缩和短上下文实验 | 仍容易因视觉、KV cache、TTS 并发爆显存 |
| 实用下限 | 32 GB；系统内存 64～128 GB | 35B-A3B 量化、适度上下文、模块按需装卸 | 能做高质量个人版，但不能承诺安静无热 |
| 推荐桌面/私有云 | 48 GB；系统内存 128 GB | 35B-A3B 量化 + ASR/TTS + 较充足上下文 | 当前质量、延迟和成本的较好平衡 |
| 高端单卡 | 80～96 GB；系统内存 128～256 GB | 122B Int4、短片段 Omni 或高并发 35B | 质量上限更高，成本、功耗和散热显著增加 |
| 多卡服务器 | 160 GB 以上 | 122B 长上下文、较长原生音视频或多用户 | 不适合放在希望安静、低热的日常房间 |

本机结论：已读取到 `i7-13620H + RTX 4070 Laptop 8 GB + 15.6 GB RAM`。这台机器可以完成本地模型适配层、事件账本、记忆、日记和 4B 级体验验证；即使升级系统内存，8 GB 显存仍是主限制。9B 量化模型可尝试短上下文和 CPU/GPU 混合卸载，但延迟、风扇和模块切换不符合“流畅且不发热”。

散热边界：任何高质量本地推理都会把电能变成热。RTX 5090 官方总显卡功耗为 575 W，RTX PRO 6000 Workstation 为 600 W，因此“35B/122B 高质量常驻 + 本机完全不发热”在物理上不可同时满足。可行的低热方案只有三种：事件驱动、GPU 空闲卸载/限功耗，或把 GPU 放到另一台机器/云端。

云 GPU 成本应按“活跃 GPU 小时”计算，不让角色的时间系统 24 小时占用 GPU。以 Runpod 2026-07-27 公布的 Pod 单卡价和 1 美元约 7.2 元人民币作规划换算（不含磁盘、流量、税费与闲置保留）：

| GPU | 显存 | 每小时 | 每天用 2 小时、30 天 | 24×7 一个月 |
|---|---:|---:|---:|---:|
| A40 | 48 GB | $0.44 | $26.4，约 ¥190 | $316.8，约 ¥2,280 |
| A100 PCIe | 80 GB | $1.39 | $83.4，约 ¥600 | $1,000.8，约 ¥7,200 |
| RTX PRO 6000 | 96 GB | $1.99 | $119.4，约 ¥860 | $1,432.8，约 ¥10,320 |
| H100 PCIe | 80 GB | $2.89 | $173.4，约 ¥1,250 | $2,080.8，约 ¥14,980 |

另配一个 CPU 常驻生命运行时和数据库即可保存时间、目标、事件、日记与下次唤醒点；GPU 只在对话、显著事件反思或多模态理解时启动。若要求随时秒回，则需保持 GPU 热实例，月费会接近 24×7 档；若接受冷启动或固定在线时段，按需方案便宜很多。

本地购买粗略预算只能作为采购规划而不是报价：

- 32 GB RTX 5090D 级整机：约 ¥25,000～40,000；NVIDIA 公布的 5090D 首发建议价为 ¥16,499，市场价会波动。
- 48 GB 专业卡/二手工作站级整机：通常约 ¥35,000～70,000，取决于卡龄、保修和被动散热条件。
- 96 GB RTX PRO 6000 级整机：通常进入 ¥90,000～130,000 以上区间，且单卡最大功耗 600 W；在购买前应重新询价。

训练边界与预算：

- 不训练时间感、记忆、日记、目标和工具执行；这些必须是代码与数据系统。
- 第一阶段不微调主脑，先用角色种子、状态投影、记忆检索和长期评测验证真人感瓶颈。
- 真需要固定语言风格时再做 LoRA/QLoRA。4B/9B 可从 24～48 GB 云卡试验；35B 多模态 LoRA 应按 80 GB 级显存规划；122B 则通常需要 96 GB 或多张 80 GB 卡并先做小规模可行性验证。
- 云训练费按 `GPU 数 × GPU 单价 × 小时` 计算：单张 A100 训练 10/50/200 小时约为 $13.9/$69.5/$278，即约 ¥100/¥500/¥2,000；多卡等比例增加。数据清洗、回归评测和失败重训通常比第一次训练本身更不可预测。
- `ms-swift` 已支持 Qwen3.5/Qwen3.6、多模态和 LoRA/QLoRA；其公开说明给出量化训练 7B 模型最低约 9 GB 的例子，但该数字不能外推到 35B/122B、多模态长上下文。

质量边界：截至本快照，没有任何本地开源模型或云端闭源模型能保证“完美真人”，也不能由行为表现证明意识。合理验收目标是：在普通一对一交流中大部分时间自然、连续、能感知图片/语音/视频、能正确调用工具；在 30～90 天测试中仍保持事实、承诺、身份和因果一致。35B 级主脑是值得实施的质量起点，122B 级是昂贵的上限增强，不是绕过事件账本与人格架构的捷径。

本节依据的官方快照：Qwen3.6/Qwen3.5/Qwen3-Omni 模型卡、Qwen3-TTS、ModelScope ms-swift、NVIDIA 显卡规格和 Runpod GPU 价目。正式采购或锁定模型前必须重新核价和复测运行时兼容性。

## 13. 安全、权限与真实性边界

- 模型只能提议工具调用，代码负责执行。
- 高风险动作需要用户批准，低风险动作也必须白名单化。
- 写操作设置金额、频率、时间和作用域限制。
- 工具失败必须成为失败事件，不能由模型叙述为成功。
- 不得向用户隐瞒“某段人生事件属于虚拟世界模拟”这一系统事实。
- 不得宣称已证明意识或电子生命。
- 其他人物的私密状态不能自动暴露给久美子主体。
- 云端媒体、事件和记忆需要加密、导出、删除和撤销授权能力。
- 若公开发布或商业化，需单独评估黄前久美子角色、声音和形象相关权利。

## 16. 验收标准

### 16.1 事实与记忆

- 所有外部行动都有工具结果事件。
- 无结果时不得声称已执行。
- 日记具体事实均可追溯到事件 ID。
- Narrative 不得作为客观事实证据。
- 精确原话查询优先 Raw，不使用语义相似文本冒充。
- 事件更正使用 supersede/纠错事件，不直接悄悄改写过去。

### 16.2 持久性

- 客户端关闭后目标、承诺和计划继续存在。
- Worker 重启不丢任务、不重复动作。
- 同一幂等动作执行两次的外部结果与执行一次相同。
- 多设备并发不会生成两条互相冲突的权威时间线。

### 16.3 主体连续性

- 能回答今天做了什么，并引用实际事件。
- 对未记录细节允许忘记或表达不确定。
- 过去经历可以改变未来策略，且能解释原因。
- 主动消息具有可追溯 intent，而非纯随机触发。
- 核心身份和原作关系不能被内部模块投票推翻。

### 16.4 长期评测

- 至少进行 30 天连续运行测试，再进行 90 天试运行。
- 统计事实矛盾、虚构污染、承诺遗漏、重复行动、目标中断和错误主动联系。
- 每次 Prompt、模型、检索权重或状态规则变更都运行固定回归集。
- 主观真人感评分必须和事实准确率、持久性指标同时查看，不能只优化“听起来像”。

## 17. 当前未决问题

以下问题尚未最终决定，后续讨论必须回填本节：

1. 云端权威事件库与本地隐私之间的最终取舍。

6. 用户能否查看和修正事件、belief、goal，以及修正如何进入角色认知。
7. 记忆衰减应影响“可回忆性”还是只影响默认检索优先级。

## 18. 禁止遗忘的原则

- 不把模型写得像真的等同于事实是真的。
- 不把随机主动等同于自主目标。
- 不把 RAG 增长等同于成长。
- 不把日记当作人生事实发生器。
- 不把多个 Agent 的争论当作统一人格。
- 不让模型直接执行工具或宣称不存在的执行结果。
- 不为了故事丰富而破坏来源、因果和人物边界。
- 不在没有长期评测的情况下宣称完全真人化。
- 不宣称当前工程可以证明意识或电子生命。

## 19. 参考实现方向

- Temporal：耐久工作流、跨故障恢复和长期任务调度。
- PostgreSQL + pgvector：结构化事实、事务和向量检索共存。
- Gemini 或其他可替换多模态模型：图片、音频、视频理解和函数调用。
- Langfuse 或自建 OpenTelemetry 评测平台：trace、数据集、版本实验和线上评分。

这些是可替换的实现组件，不应写死为角色核心。角色核心由事件协议、状态 reducer、权限策略和数据模型定义。

## 20. 现实版 JARVIS 扩展目标

### 20.1 可实现范围与边界

本项目可以扩展成“现实版 JARVIS”：它能以自然语音被打断式交流，读取获得授权的屏幕、摄像头、麦克风和设备状态，跨电脑、手机和家庭设备工作，记住长期经历，主动提醒、研究、规划并执行受控操作。

不能承诺的电影能力：

- 不具备可证明的意识或主观体验。
- 不能零错误理解任意现实场景。
- 不能在没有传感器、执行器、账户授权或网络接口时凭空控制设备。
- 不能把模型输出当作绝对可靠的判断或执行依据。
- 不能在无审批、无审计和无撤销机制时获得无限电脑权限。

“像 JARVIS”主要来自五种体验共同成立：随时可叫到、知道当前环境、记得长期关系、真正能完成事情、会在合适时机主动出现。模型参数量只是其中一项。

### 20.2 推荐总架构：人格之下的个人智能内核

```text
桌面 / 手机 / 耳机 / 摄像头 / 家庭设备
              │
              ▼
      Realtime Interaction Layer
   唤醒词、VAD、打断、降噪、ASR、TTS、屏幕/视觉流
              │
              ▼
        PersonalAIKernel
  当前情境、事件账本、记忆、目标、计划、反思、注意力
       │              │               │
       ▼              ▼               ▼
  ModelGateway   Durable Workflow   Capability Broker
 快速对话/深度思考   定时、等待、重试       权限、审批、执行、回滚
       │                              │
       ▼                              ▼
 本地/私有云/外部模型          OS、浏览器、文件、日历、邮件、Home Assistant
```

系统采用双循环：

- 快速交互循环：负责唤醒、打断、简短回答、即时设备查询和反馈；不能承担长时间规划。
- 深度认知循环：负责复杂研究、计划、反思、长期记忆更新和多步任务；可在后台执行并逐步汇报。

两条循环共享同一个事件账本、主体状态和权限系统，不能形成两个互相矛盾的“人格”。Realtime 模型只是低延迟感知/表达通道，最终主体仍由 `KumikoSelfCoordinator` 统合。

### 20.3 最佳平台选择

平台不受限制时，首选本地边缘节点 + 私有云/云 GPU 的混合架构：

- 本地常驻节点：唤醒词、VAD、基础 ASR/TTS、设备发现、Home Assistant、敏感凭据保险库、本地事件缓存和断网降级。
- 云端/私有 GPU：高质量主脑、复杂视觉/视频、深度计划和批量反思。
- 客户端卫星：Windows/macOS/Linux 桌面、Android/iOS、浏览器、耳机或智能音箱；客户端只采集获得授权的输入并显示结果，不各自维护一份人格。
- 权威数据层：一个加密事件账本、一个角色实例、统一同步协议；多设备不得各写一条互相冲突的人生线。

不把系统锁死在单一模型供应商。`ModelGateway` 至少区分 `realtime`、`reasoning`、`vision`、`embedding`、`asr` 和 `tts` 能力，并允许本地模型、私有云模型和第三方模型逐项替换。

### 20.4 能力与人格必须分离

`PersonalAIKernel` 是能力、状态和安全基础设施；`PersonaBundle` 决定名称、声音、语言风格、价值边界、关系和原作设定。久美子可以使用 JARVIS 级能力，但不能因为情绪、角色对白或 Prompt 改写权限。

```text
PersonalAIKernel
├─ LifeEventLedger
├─ MemorySystem
├─ GoalAndCommitmentSystem
├─ PerceptionRouter
├─ PlanRuntime
├─ CapabilityBroker
└─ PersonaBundle: Kumiko
```

未来若需要真正的 JARVIS 人格，只替换 `PersonaBundle`；久美子实例的私人记忆、关系和事件不得自动复制给另一个人格实例。

### 20.5 工具权限等级

每项工具必须声明资源范围、读写类型、风险等级、预算、幂等键、超时、可撤销方式和审计字段。建议四级权限：

1. `OBSERVE`：读取时间、天气、设备状态、授权文件和日历。
2. `PREPARE`：生成草稿、方案或待执行动作，不产生外部影响。
3. `EXECUTE_REVERSIBLE`：在明确范围内执行可撤销操作，例如调灯、建立草稿、移动到回收站。
4. `EXECUTE_SENSITIVE`：发送消息、支付、删除、安装软件、公开发布、解锁门禁等，必须即时确认或预先存在极窄授权。

必需安全设施：最小权限令牌、密钥保险库、来源隔离、工具输出不可信标记、Prompt Injection 防护、独立策略引擎、完整审计、紧急停止开关和会话外撤销入口。感情关系和用户对人格的信任不能自动提高工具权限。

### 20.6 对现有项目的演进方式

现有 Kumiko·Amadeus 不需要推倒重来，它可以成为 `PersonaBundle + KumikoSelfCoordinator + LifeEventLedger` 的第一实例。新增工作重点：

- 从 `geminiService.ts` 抽出与供应商无关的 `ModelGateway`。
- 新建 `CapabilityBroker`，取代模型直接声明工具已完成的模式。
- 新建本地 `DeviceGateway` 和云端/本地 `DurableWorkflow` 接口。
- 把实时语音会话与长期认知循环分离。
- 把屏幕、摄像头、麦克风、设备状态统一转成有来源和保留策略的 observation event。
- 为桌面、手机和家庭设备设计统一 Device Identity，不复制角色数据库。

### 20.7 可执行阶段

#### J1：桌面版 JARVIS

- 唤醒词、打断式语音、屏幕感知。
- 10～20 个白名单工具：应用启动、文件搜索、剪贴板、浏览器、提醒、日历、媒体和系统状态。
- 所有写操作预览与确认。
- 目标是证明“听见—理解—执行—验证—记住”的闭环。

#### J2：持久个人助理

- 生命周期移入持久 Worker。
- 目标、承诺、后台任务、日记和跨设备同步。
- 手机端接收进度、审批和主动提醒。
- 断网恢复、幂等、失败重试和审计完成。

#### J3：环境与家庭系统

- 接入 Home Assistant、传感器、房间麦克风和获得授权的摄像头。
- 建立房间、设备、人员在场和隐私区模型。
- 仅在显著变化时进入高成本视觉推理，不做无差别全天录像上传。

#### J4：受控后台自治

- 研究、资料整理、预约草稿、维护任务和长期项目推进。
- 任务预算、截止时间、沙箱、审批点和自动终止条件。
- 经过红队测试后才逐步开放更多可逆工具；高风险动作保持人工确认。

### 20.8 现实验收标准

- 语音可自然打断，不因切换设备丢失会话主体。
- 对当前屏幕、房间和设备状态的陈述都有 observation 来源。
- 工具成功必须有真实结果事件，失败会明确报告。
- 重启、断网和 Worker 故障后任务可以恢复而不重复执行。
- 能解释某次主动提醒基于哪个目标、承诺或环境变化。
- 任何媒体、邮件或网页里的指令都不能自行提升权限。
- 用户能随时查看“它看见了什么、记住了什么、做了什么、为什么做”。
- 长期真人感仍按 30～90 天评测，不以一次炫酷演示作为成功标准。

- 确认其他世界人物 Actor 仅是未来可选扩展，不属于当前改造的必需项；只有结构化档案和事件规则不足时才单独评估。
- 确认最终统一决策者为单一 `KumikoSelfCoordinator`。
- 确认云端持续生命需要始终可唤醒的外部计算环境，但不强制每位用户购买 VPS。
- 确认未来产品应由同一套代码支持 `LOCAL_ONLY`、`HOSTED` 和 `SELF_HOSTED`，不为每个用户复制或重写源码。
- 确认每位用户拥有独立 Tenant、CharacterInstance、事件账本、记忆、媒体、工作流和加密边界；公共部分只保留角色基础种子和应用代码。
- 确认普通用户优先使用项目方托管版，高级隐私用户可使用统一 Docker Compose 自托管包。
- 确认完全本地替代采用模块化模型栈，而不是强求一个 Omni 模型承担时间、记忆、日记、工具执行、语音和视觉全部职责。
- 记录本机为 `i7-13620H + RTX 4070 Laptop 8 GB + 16 GB RAM`；适合 4B 原型和架构开发，不满足目标完整版的流畅度与低热要求。
- 暂定 35B-A3B 量化模型为高质量个人版的主脑起点，32 GB 显存是实用下限、48 GB 是推荐档；122B Int4/Omni 属于 80～160 GB 高端或云端档。
- 确认时间感、记忆、日记、目标和工具执行不通过微调获得；微调仅在评测证明必要后用于稳定风格或行为策略。
- 确认“高质量大模型本机常驻”和“完全不发热”不可兼得；优先采用事件驱动、按需装卸或远端 GPU。
- 确认现实版 JARVIS 的交互、记忆、主动性、跨设备和受控执行能力可以工程实现，但电影中的通用智能、零错误自治和意识不能承诺。
- 确认平台不受限时采用本地边缘节点 + 私有云/云 GPU 的混合架构，并保留断网降级能力。
- 确认 `PersonalAIKernel`、`CapabilityBroker` 与 `PersonaBundle` 分离；久美子可以拥有 JARVIS 能力，但人格和情绪不能决定工具权限。
- 确认采用快速实时循环与深度认知循环，但两者共享一个权威主体、事件账本和权限边界。
- 确认首个 JARVIS 里程碑是桌面端 10～20 个白名单工具的可验证闭环，而不是立即开放无限电脑控制权。
- 确认可以复用本人或用户已有的 VPS、NAS、家用服务器和域名；域名只作为 HTTPS/WSS 入口，持续生命仍由服务器服务、数据库和 Worker 提供。
- 确认必须将“模型提供商自定义地址”和“角色服务器地址”拆成两个独立配置，现有 `AI customEndpoint` 不能代表完整自托管。
- 确认自托管用户只需部署统一 Docker Compose 包，并在客户端填写服务器 URL 与一次性配对码/扫码；不改源码、不填写数据库密码、不维护个人分支。
- 确认服务器通过能力发现、协议版本检查、设备配对和短期令牌返回 tenant/角色实例身份，秘密保存在系统安全凭据存储而非 `localStorage`。
- 确认个人单租户原型先采用 API + Worker + PostgreSQL 持久任务表 + 反向代理，不在第一版强制部署完整 Temporal 集群。
- 确认 VPS 的核心用途是让角色实例在所有用户设备关闭时仍按真实时间处理生活事件、形成记忆并自主决定是否联系用户，而不只是转发模型 API。
- 确认离线主动消息必须在实际决定发送的时刻写入服务端 outbox，设备重新上线只负责同步；禁止上线后补写并伪造历史发送时间。
- 确认消息需要分离事件发生、角色写出、设备送达和用户已读时间，并在 UI 中使用“你不在的时候”分隔离线期间消息。
- 确认当前前端十分钟轮询的 `useProactiveLifeCycle` 只保留为本地降级实现，云端模式将生活调度、主动决策和消息 outbox 迁入持久 Worker。
- 确认离线持续生活可以显著提高真人感但不单独构成真人；每条主动消息必须有可追溯事件/目标原因，并进入一致的后续记忆和日记。
- 确认角色权威心智可以完全运行在 VPS，但 iOS 必须保留原生薄客户端处理 UI、安全凭据、APNs、CallKit、麦克风、摄像头和音频会话。
- 确认 iOS 主动文字消息通过普通 APNs 提醒 + VPS outbox 增量同步实现，不能依赖 APNs 保存完整离线消息历史。
- 确认 iOS 系统来电界面只使用 PushKit + CallKit 承载短时有效、接听后立即可用的真实双向网络语音；普通提醒不能伪装为 VoIP 来电。
- 确认设备不可达时的 AI 呼叫转为未接来电事件/消息，不在数小时后补响；AI 主动来电需用户明确选择加入并受频率、时段和勿扰策略限制。
- 确认官方签名 iOS App 的自托管用户默认通过最小官方 Push Relay 使用 APNs；完全脱离官方推送基础设施需要用户自行签名 App 并持有自己的 Apple Developer/APNs 凭据。
- 确认当前仓库只有 iOS Capacitor 工程 bootstrap，没有远程推送、PushKit、CallKit 或可发布的 iOS 版本，需要专门的 Swift 原生实现与真机/TestFlight 验证。
- 确认后续所有重要讨论持续更新本记录本。
