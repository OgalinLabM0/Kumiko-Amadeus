# 久美子如何知道用户在哪里

状态：规则已确认；基础持久化与隔离检查完成。2026-11-01补强已接入主聊天协调器，加入前置事实、撤回、来源/版本与恢复代次检查；真实模型和设备验收待完成，见[意图与记忆方案](../plans/intent-and-memory-reliability.md)。

## 用户确认的规则

久美子按日本时间生活。她对用户的了解来自双方交流，不能自动知道软件设置、设备时区或IP定位。

用户告诉她“我在武汉”，她才知道用户在武汉，此后可以知道武汉的当地时间，也可以主动查武汉的天气、自然地关心用户。用户只把软件时区改成夏威夷，并没有告诉她搬家，她仍认为用户在武汉。只有用户再次明确说出新位置，这份认识才更新。

## 提醒怎样执行

- 已经保存的提醒固定原约定。一次性提醒保存具体时刻；每天重复的提醒保存创建时采用的时区和钟点，按该地区的夏令时规则计算每次时刻。以后改设置、告知搬家，都不会擅自改写已有约定。
- 新提出的“晚上8点”，优先按她已知且已确认时区的地区理解；明确说“日本时间”等，以用户的说明为准。
- 从未告知所在地时，程序可以使用请求时的软件时区换算，但不会把这个隐藏设置提供给角色。
- 已经告知地区但城市有歧义、暂时无法解析时，不借用软件设置假装知道该地钟点；需要明确城市或时间依据。相对的“十分钟后”不依赖地区。
- 程序把实际到期时刻换算成日本时间。提醒时不把日本早上当成用户早上；可以说“你之前让我提醒的洗衣服，别忘了”，不必报时。只有已知地区或用户原话足以支持时，才能谈对方的早晚。
- 提前准备回复使用约定发送时刻；迟到的提醒承认错过原时刻。

## 已实现的保存与来源约束

`user_known_location_v1` 单独保存地点、用户原话、消息ID和时间、解析状态。它与软件的 `locationConfig` 分开。模型只能提出来自本轮用户原话的候选；真正保存由协调器核对数据库中的当前用户消息，主动消息、提醒预热和改写不能冒充用户披露。

新地点先保存为待解析，再查询地名。解析失败仍记得用户说过这个地区，但当地时间和天气保持未知。旧地点尚未返回的查询不能覆盖新地点，也不能冒充新地区的天气。

天气工具 `query_known_user_weather` 只读这份已知位置，不接受模型另传地点或调用设备/IP定位。时间和天气解析使用 [Open-Meteo地名接口](https://open-meteo.com/en/docs/geocoding-api) 与天气接口；重名地点不直接选第一个结果。

位置记录随本地保存和手动备份保留；旧备份缺少该字段不会从设置中生成一份位置认知。普通聊天、摘要、回忆辅助和提醒提示已去掉隐藏用户时钟/天气的自动注入。

## 验证边界

已检查：披露来源、否定/转述/假设拒绝、重启后保留、软件设置变化不改变认知、新披露覆盖旧地点、旧查询失效、备份往返、提醒跨日/跨年/夏令时、中英混写PM、真实生产创建路径。

隔离检查不等于模型真实调用或真机验收。新披露需要模型输出结构化候选；无法确认的表达不会保存。没有扫描或清洗用户旧记忆，也没有替用户修改任何已有提醒。首次告知可在同轮先保存/解析再查询；尚未查询成功时不能声称查过。明确离开/撤回但新地点未知时，不继续查旧地区作为当前位置。后续对话或主动消息仍可选择调用已知地区天气工具。桌面/Android实机、付费模型与在线天气端到端仍待验证。
